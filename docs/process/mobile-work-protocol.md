# Tower 모바일 Work 착수·정합 프로토콜

## 목적

휴대폰의 Codex Work와 Notion에서 Tower 작업을 시작할 수 있게 하면서, 오래된 문서가 최신 소유자 결정을 자동으로 무효화하거나 모바일 세션이 구현 상태를 과장하는 일을 막는다.

이 프로토콜은 “어느 앱 하나가 전체 정본”이라는 단일 규칙 대신, 산출물마다 다른 권한과 상태를 기록한다.

## 네 축 상태 모델

모든 Tower 제안·결정·태스크는 가능하면 다음 네 축을 함께 적는다.

| 축 | 값 | 의미 |
| --- | --- | --- |
| 출처 권한 | 소유자 직접 입력 / 에이전트 제안 / 외부 참고 | 누가 의도를 만들었는가 |
| 설계 성숙도 | 탐색 / 소유자 결정 / 태스크 브리프 | 얼마나 결정됐는가 |
| 동기화 | 대기 / 대조 완료 / 대체됨 | Notion·vault·GitHub 사이 정합 상태 |
| 구현 | 미착수 / 브랜치 / Draft PR / 머지 / 런타임 검증 | 실제 제품 반영 정도 |

“비정본”이라는 말만 단독으로 사용하지 않는다. 예를 들어 소유자 대화에서 나온 아이디어는 **소유자 직접 입력 / 탐색 / vault 대조 대기 / 미착수**일 수 있다. 탐색이라는 이유로 무효가 되지는 않으며, 소유자 결정이라는 이유만으로 구현 완료가 되지도 않는다.

## 표면별 역할

- **Notion `Creations / Tower`**: 모바일 인입·작업 지시·결정 캡처·진행 링크를 모으는 제어면. 소유자가 직접 내린 명시적 결정은 유효한 의도 출처다.
- **로컬 Tower vault** `C:\Users\fancy\Personal Agent Memory\40_Projects\Tower\`: 장기 설계, 결정 이력, 현재 상태를 정리한 내구성 있는 통합 기록.
- **GitHub** `team-muel/tower`: 코드·태스크 브리프·브랜치·PR의 구현 진실.
- **빌드와 테스트 증적**: 실제 동작과 완료 여부의 검증 진실.
- **`AGENTS.md`**: 위 표면으로 안내하는 작업 계약이자 요약 미러. 오래된 한 줄 요약을 독립 정본으로 사용하지 않는다.

## 충돌 판정

1. 같은 범위에서 날짜가 명확한 최신 소유자 결정은 오래된 요약보다 우선한다.
2. 소유자 결정과 vault가 다르면 결정을 “비정본”으로 강등하지 않고 **동기화 대기**로 기록한다.
3. 게임 의도는 소유자 결정과 정합 문서가 설명한다. 실제 구현 상태는 GitHub와 빌드 증적이 설명한다.
4. 제품 정체성 자체가 충돌하면, 예를 들어 “현행 Tower 피벗”인지 “별도 AA 신작”인지 불분명하면 에이전트는 공통 기반 문서·격리 스파이크까지만 진행하고 제품 코드 머지는 보류한다.
5. 로컬 vault에 접근할 수 없다는 사실은 문서화·태스크 설계·격리 브랜치 착수를 막지 않는다. 다만 접근했다고 주장하거나 대조 완료로 표시해서는 안 된다.

## 휴대폰에서 시작하는 방법

Notion Tower 부모 페이지 아래에 새 작업 패킷을 만들거나 Work 대화에서 아래 항목을 명시한다.

### 모바일 작업 패킷

- **제목**: `[Tower] 원하는 결과`
- **대상 제품**: 현행 Tower / AA 액션 방향 / 미결
- **소유자 결정**: 이번 작업에서 새로 확정한 문장
- **목표**: 이번 태스크가 끝나면 관찰 가능한 결과
- **범위**: 바꿔도 되는 문서·코드·씬
- **하지 않을 것**: 발명 금지 또는 후속 범위
- **완료 증거**: 문서 재조회, 테스트, Windows 빌드, 스크린샷 등
- **참고 링크**: Notion 페이지, GitHub PR/파일, 필요한 외부 근거
- **현재 네 축 상태**: 출처 권한 / 설계 성숙도 / 동기화 / 구현

짧게 시작하려면 다음 문장만으로도 된다.

> Tower 작업 시작. 대상 제품: ___. 목표: ___. 하지 않을 것: ___. 완료 증거: ___. 이 지시는 소유자 결정 / 동기화 대기로 기록.

## 에이전트 착수 순서

1. Notion Tower 부모 페이지와 지정된 작업 패킷을 읽는다.
2. GitHub 커넥터로 `AGENTS.md`, 관련 PR, 브랜치와 태스크 번호를 확인한다.
3. 로컬 vault에 접근 가능하면 `00 Current Status.md`와 관련 설계 문서를 대조한다.
4. 접근 불가 또는 충돌이면 PR 본문에 **동기화 대기**와 정확한 충돌 문장을 적는다.
5. 사용 가능한 다음 T 번호를 GitHub 브랜치·PR에서 확인하고 `task/T<N>-<slug>` 브랜치를 만든다.
6. `docs/tasks/T<N>.md`에 목표, 범위, 비범위, 완료 증거, 결정 출처와 정합 상태를 적는다.
7. 코드 변경은 그 브랜치에서만 수행하고 Draft PR을 연다. `main` 직접 푸시는 금지한다.
8. 작업 후 Notion 패킷에 브랜치·PR·검증 결과를 되돌려 적는다.

## 모바일에서 허용되는 착수

로컬 vault를 읽지 못해도 다음은 시작할 수 있다.

- 대화·결정 기록
- 리서치와 비교 문서
- 태스크 브리프
- 기존 코드와 격리된 기술 스파이크
- GitHub Draft PR
- 실패해도 되돌릴 수 있는 테스트 추가

다음은 정합 전 보류한다.

- 제품 정체성을 되돌리기 어려운 전면 피벗
- 기존 세이브·데이터 계약 파괴
- `main` 머지
- 기존 구현을 대량 삭제하는 작업
- 검증하지 않은 문서를 “현재 구현 완료”로 표시하는 일

## 데스크톱 정합 게이트

Draft PR을 Ready 또는 merge 상태로 바꾸기 전에 가능한 범위에서 다음을 수행한다.

1. 로컬 vault의 최신 상태와 모바일 결정의 범위를 대조한다.
2. 최신 소유자 결정이 기존 문서를 대체하면 `00 Current Status.md`와 관련 설계 문서를 갱신한다.
3. `AGENTS.md`의 요약이 다시 오래되지 않게 고정 설계 문구보다 읽기 순서와 상태 모델을 우선한다.
4. Notion 작업 패킷의 동기화를 **대조 완료** 또는 **대체됨**으로 갱신한다.
5. GitHub PR에 테스트·빌드·스크린샷 등 실제 완료 증거를 기록한다.
