# T47 — Author the player locomotion Animator Controller

**Branch** `task/T47-locomotion-controller` · **PR title** `T47: locomotion animator controller`
**Assets** `Assets/_Tower/Art/Characters/Animations/` (controller) + scene wiring (orchestrator)

## Why (the finding that produced this task)

T46 wired `PlayerIsoController` to drive an `Animator` float parameter from actual
travelled speed. The code is correct and gated (EditMode 534/534). But the worker read
the Blink controller as YAML and reported:

> `LowPolyHumanAnimator.controller` has `m_AnimatorParameters: []`. States found: `Idle`.

So the controller **declares zero parameters and has a single Idle state**. T46's fail-soft
guard therefore disables animator driving with one warning, and the player still slides
across the forest in an idle pose. The 32 Blink clips exist; nothing plays them.

**T46 built the pipe. T47 has to put water in it.**

## v0 rules (do NOT decide these yourself)

1. **Do not modify the Blink pack in place.** Create a Tower-owned controller. Blink is a
   vendored asset-store pack; editing it makes the next re-import a merge conflict.
2. Parameter name is **`Speed`**, type **Float**, matching `PlayerIsoController.speedParameter`
   (serialized default). Do not rename it; do not add a second speed parameter.
3. `PlayerIsoController.normalizeSpeed = true` sends **0..1**, not m/s. Author the blend
   tree thresholds in that normalized space.
4. **Do not touch `PlayerIsoController.cs` or `PlayerLocomotion.cs`.** T46 landed them and
   they are tested. If you believe they are wrong, say so in the PR instead of editing.
5. Root motion **off** — the controller drives the transform.

## Deliverables

### 1. `PC_Locomotion.controller` (new, Tower-owned)

- Base layer, one state: `Locomotion`, containing a **1D Blend Tree** on `Speed`.
- Motions and thresholds (v0, tune later):

| Threshold | Clip (from Blink) |
|---|---|
| 0.0 | Idle |
| 0.5 | Walk / RunForward (slowest forward locomotion clip available) |
| 1.0 | Sprint / Run (fastest forward locomotion clip available) |

Read the actual clip names out of the Blink FBX metas — **do not guess them**. If a
distinct walk clip does not exist, use a two-motion tree (Idle → Run) and say so.

### 2. Verify the parameter contract

Write an EditMode test `LocomotionControllerTests` asserting:

- the controller asset loads at its expected path,
- it declares a Float parameter named exactly `Speed`,
- the base layer's default state contains a `BlendTree` whose blend parameter is `Speed`,
- the tree has ≥ 2 motions and its thresholds are non-decreasing.

This test is what stops the T46 regression from silently coming back.

### 3. Scene wiring (orchestrator does this after merge, not you)

Assign `PC_Locomotion` to the player's `Animator.runtimeAnimatorController` in
`Prototype.unity`, and assign the `Animator` reference on `PlayerIsoController`.

## Definition of done

- Full batchmode EditMode suite passes (≥ 534 + new tests).
- Play mode: walking with WASD blends Idle → Walk → Run; standing still returns to Idle.
  (If you cannot run play mode from a worktree, state that and rely on the EditMode test.)
- **No** `Debug.LogWarning` from `PlayerIsoController` about a missing parameter.
- No edits under `Assets/Blink/`.

## Traps

1. Blink prefab's 23 `SkinnedMeshRenderer`s have manually assigned materials and
   `PlateSet1` is deliberately disabled. Do not "fix" that here.
2. `AnimatorController` assets can only be authored through `UnityEditor.Animations`
   (Editor-only). Any authoring script belongs under an **Editor** folder / Editor asmdef,
   or the player build breaks (this exact class of bug already bit the ithappy import).
3. A non-kinematic `Rigidbody` on a tall character tips over — leave the Rigidbody alone.
4. `git -C C:\Users\fancy\Tower ...` — never `cd` then `git`. Commit with
   `-c commit.gpgsign=false`.
