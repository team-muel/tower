## Why

Vault decision (18 / 38, owner, 2026-07-08, re-confirmed 2026-07-09): the combat spine is
**real-time telegraph -> space-bar slow-mo -> multiple-answer counter**, not BG3 grid turns.
The reference is 5minlab *Revolver*'s showdown: a charge/decay slow-mo resource, `hold -> acquire
(mark) -> release`, and shader-driven feedback.

The design constraint the owner keeps repeating: **the player must never watch a companion get
hit stupidly.** You read the telegraph, you slow time, you answer.

## v0 rules (do NOT decide these yourself)

1. **Slow-mo is a charge/decay resource, not a toggle.** No infinite slow. It drains while
   engaged and refills over time. Serialize the numbers; do not bake them into code.
2. **One enemy archetype only**: 1층계 기생종 "공벌레" (pill-bug). Behaviour is a three-beat
   loop: `Idle -> Windup (telegraphed) -> Commit (short lunge)`. The windup is the readable
   window. Commit is uninterruptible.
3. **Multiple answers, not one.** At minimum the player can (a) dodge/reposition, (b) issue an
   order to a companion via the existing `OrderBoard`, (c) use an ability from
   `AbilityLoadout` / `AbilityResolver`. Do not hardcode a single correct answer.
4. **Reuse, do not rebuild.** `CombatState` (from T49), `AbilityDef` / `AbilityResolver`,
   `OrderBoard`, `ActionScorer` / `AiPlan` / `DispositionWeights`, `StatusBoard`,
   `AnalogBattlefield` / `IBattlefield` / `BattlePos` all exist and are tested. Use them.
   Companions are auto-piloted by disposition AI; the player only issues orders.
5. **Time scale is a service, not a global.** `Time.timeScale` fiddling everywhere is how this
   becomes unfixable. One `TimeDilationService` owns it; everything else asks.
6. **Pure logic in `Tower.Core`.** The charge/decay curve, the telegraph state machine, and the
   answer-window arithmetic must be testable without a scene. MonoBehaviours only drive them.
7. **No new UI assembly.** T49 dissolved `Tower.UI`. A world-space telegraph cue (ring, colour,
   scale) is enough for v0. Feedback via shader/colour, per the Revolver reference.

## Deliverables

### 1. `Tower.Core` (pure, tested)
- `SlowMoResource` — charge 0..1, `Drain(dt)`, `Recharge(dt)`, `CanEngage`, min-engage threshold.
- `TelegraphState` — `Idle | Windup | Commit | Recover`, with `Advance(float dt)` and the
  windup duration as data. Deterministic; no `UnityEngine.Random`.
- `CounterWindow` — given a telegraph and a player action time, classify
  `Early | Clean | Late | Missed`. This is the thing designers will tune.

### 2. `Tower.Combat` (MonoBehaviour layer)
- `TimeDilationService` — the only writer of `Time.timeScale`. Also scales
  `Time.fixedDeltaTime`. Exposes `float Current`. Slow-mo affects the world, **not** UI/input.
- `PillbugBrain` — drives `TelegraphState`, moves the Quaternius `Enemy_Slime` prefab as a
  stand-in, plays its Idle/Attack clips.
- `SlowMoInput` — space held -> engage while `SlowMoResource.CanEngage`; release -> resume.
- `CombatEncounterHost` — spawns 1 pillbug at a forest node, holds `CombatState`, ends when the
  enemy dies or the player leaves. **No fork-locking, no wave logic** (that is a later task).

### 3. Scene
Do **not** edit `Prototype.unity`. Add a scratch scene
`Assets/_Tower/Scenes/_CombatSpike.unity` so the orchestrator can wire and judge it. The
orchestrator promotes it into the build scene once the feel is approved.

### 4. Tests (`Assets/_Tower/Tests/EditMode/`)
- `SlowMoResourceTests`: drain to zero forces disengage; recharge is monotonic; `CanEngage`
  respects the minimum threshold; drain/recharge are frame-rate independent (same result for
  1x0.5s and 50x0.01s).
- `TelegraphStateTests`: Windup always precedes Commit; Commit cannot be re-entered mid-Commit;
  total cycle time equals the sum of the phase durations.
- `CounterWindowTests`: boundary classification at exactly the window edges; a response during
  Commit is always `Missed`.

## Traps

1. `Time.timeScale` also scales `Time.deltaTime`. Anything that must stay real-time (input,
   camera feel, the slow-mo resource itself) must use `Time.unscaledDeltaTime`.
   `IsoCameraFollow` already uses `unscaledDeltaTime` — do not "fix" it.
2. Setting `Time.timeScale` without also setting `Time.fixedDeltaTime` makes physics stutter.
3. `PlayerIsoController` drives the transform and its Animator via **measured** planar speed
   (T46). If you slow time, measured speed drops and the character will walk in slow motion —
   which is probably right, but verify it looks intentional and say so.
4. A non-kinematic `Rigidbody` on a tall character tips over. Keep `isKinematic = true`.
5. No `UnityEngine.Random` in code. Determinism is the project contract.
6. `git -C C:\dev\tower-wt-T48 ...` — never `cd` then `git`. Commit with `-c commit.gpgsign=false`.
